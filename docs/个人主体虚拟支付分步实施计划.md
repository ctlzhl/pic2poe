# 个人虚拟支付与创作次数 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 先建立可测试的创作次数账本，再按个人主体官方指引接入真实支付，以一次小规模试运行验证付费意愿和成本覆盖。

**Architecture:** 保留小程序、CloudBase 云函数和私有文档数据库。`createCreation` 预留额度，创作成功事务确认消耗，失败事务释放；订单必须由服务端核验支付后才发放。支付端采用个人主体的道具直购，客户端负责调起支付，服务端以发货推送为主、查单为兜底确认交易；支付平台适配与真机验收受实际后台权限和官方接口契约约束，不能用普通商户支付接口代替。

**Tech Stack:** 微信小程序、CloudBase 云函数 Node.js 20.19、CloudBase 文档数据库事务、`node:test`。

**Spec:** [个人主体虚拟支付与创作次数设计](./个人主体虚拟支付与创作次数设计.md)。

## Global Constraints

- 唯一付费商品：「5 次创作包」，试验价 ¥2.9，不自动续费；三种创作类型每份成功作品消耗 1 次。
- 新用户一次性赠送 3 次，每个北京时间自然日免费 1 次；上线前已有成功作品的老用户以 10 次过渡额度替代 3 次新用户额度；首测期间已购额度不过期。
- 额度使用顺序：今日免费、首次或过渡赠送、已购额度；已购额度按最早的有效订单使用。
- 同一 attempt 只预留 1 次，作品成功后消耗，失败与超时释放；用户主动重试产生新 attempt 和新预留，模型内部重试不新增预留。
- 原有限流 10 分钟 4 次、24 小时 20 次独立保留；保存、分享、首页和博客不收费。
- `creationWallets`、`creationReservations`、`virtualPaymentOrders`、`creationCreditLedger` 均为私有集合；客户端不得直接写入；服务端以 `OPENID` 校验归属。
- 不复用 `poemRecords`，不引入云托管、Redis、常驻进程或普通商户号支付链路；密钥不得进入小程序包、数据库或 Git。
- 工作区在制定计划时已有未提交的 `runCreation`、`createShareCard` 和文档改动。执行每个任务前先复查状态；涉及重叠文件时保留并融合这些改动，不批量提交无关文件。
- 第一阶段的额度代码不得单独部署到正式环境，否则现有免费用户可能突然被拦截；必须等真实支付、页面说明与服务端对账整体验收后上线。
- 一个道具代表「5 次创作包」，一次订单的 `buyQuantity` 固定为 1、道具价格固定为 290 分；服务端只接受这一种商品配置，不能把「5 次」误传为 5 件道具。
- 客户端 `wx.requestVirtualPayment` 的成功回调只触发查询，不能更新订单或余额；平台发货推送或服务端 `query_order` 确认后，才能在事务中发放 5 次。
- 已安装的 `personal-virtual-payment` v1.0.2 技能提供接入参考及清单，但它不是本环境已读取的微信官网原文。签名字段、推送验真、HTTP 入口、退款和终端能力在执行前必须与实际后台及官方当前契约核对。

## 范围与关口

本计划把工程拆为三个交付阶段。阶段 A 可根据当前仓库直接实施并本地验收；阶段 B 已按[本地技能指引](/Users/michael/.codex/skills/@tencent-adm/miniprogram-virtualpay-person/SKILL.md)拆成工程任务，但第一项必须完成「实际平台契约核对」；阶段 C 才能进行云端和真机发布。当前环境仍无法直接读取[微信官网个人主体指引](https://developers.weixin.qq.com/miniprogram/dev/platform-capabilities/business-capabilities/virtual-payment/person)，因此技能中的字段和示例仅作为待核对的候选契约，不视为正式验收证据。阶段 A 完成不等于支付接入完成。

## 文件职责图

阶段 A 新增 `cloudfunctions/createCreation/credit-policy.js` 作为额度选择和钱包初始化规则，`cloudfunctions/createCreation/credit-policy.test.js` 验证边界；现有 `createCreation` 增加 `action: 'getCredits'`，仅向当前用户返回钱包摘要，避免为读取余额另开一套钱包初始化实现。`createCreation/index.js` 负责第一次 attempt 的事务预留；`retryCreation/index.js` 负责主动重试的新 attempt 预留；`runCreation/index.js` 负责成功或执行失败的事务结算；`getCreation/index.js` 与 `recoverStuckTasks/index.js` 负责各自将超时任务置为失败时的释放。云函数彼此独立打包，因此每个会改变任务终态的函数都在自身事务中更新预留，不能跨函数调用来代替原子结算。`cloudbaserc.json` 登记新增的补偿函数；`docs/P1-云端配置与验收.md` 增加四个私有集合、必要索引和部署前条件。

阶段 B 建立 `cloudfunctions/virtualPayment/` 处理当前用户的下单、订单查询和列表；建立独立的 `cloudfunctions/virtualPaymentNotify/` 作为平台发货/退款推送入口；建立 `cloudfunctions/reconcileVirtualPaymentOrders/` 定时查单补发货。三个函数目录各自独立打包，不能从兄弟目录运行时导入文件；若有同一结算规则的副本，以共享测试向量约束它们一致。小程序侧修改 `pages/index/index.js`、`.wxml`、`.wxss` 及其测试，购买浮层保持在创作页内；`pages/my/` 只新增轻量权益与订单入口。阶段 C 的成本汇总从 `creationAttempts.modelMeta` 和平台账单读取，不在客户端计算收入或余额。

1. **资格和后台：**个人主体、中国大陆居民身份证、工具类目、认证备案、全终端月限额已告知；虚拟支付已开通并签约；AppID/OfferID/现网 AppKey 已在后台取得，AppKey 仅存云端。iOS 如开放购买，另核对小程序简称、IAP 开通和终端版本。证据为脱敏后台截图及配置探针，不在验收文件中写密钥。
